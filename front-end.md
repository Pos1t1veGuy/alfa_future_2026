ЧАСТЬ 1. FRONTEND_SPEC.md
1.1. Технологический стек и структура
React + Vite + TypeScript

React Router v6 — маршрутизация с guard'ами по ролям

TanStack Query — серверное состояние, кеш, ретраи, инвалидация

React Hook Form + Zod — формы и валидация

Axios — HTTP-клиент с интерсепторами (токен, ошибки)

MSW (Mock Service Worker) — мок-слой для работы без бэкенда

Tailwind CSS или UI-kit (shadcn/ui, MUI — на выбор команды)

Zustand — только для UI-состояния (тема, сайдбар, wizard-step), не для серверных данных

Guard-логика: RequireAuth проверяет валидный access-токен, RequireRole — роль из JWT//me. При 401 — refresh, при неудаче — logout и редирект на /login?redirect=....

1.3. Экраны и функции — детально
Экран: Логин (/login)
Поля: email, пароль.

Валидация: email-формат, пароль не пустой.

Ошибки: «Неверный email или пароль», «Аккаунт заблокирован».

После успеха — редирект по роли (client → /client/applications, bank_manager → /bank/applications).

Блок «Тестовые аккаунты» для демо (только в dev/demo-режиме): клиент и менеджер с готовыми кредами.

Индикатор загрузки, блокировка кнопки при отправке.

Экран: Дашборд клиента (/client/applications)
Список заявок: номер, продукт, сумма, статус-бейдж, дата создания, дата обновления.

Сортировка по дате, фильтр по статусу (Все / В работе / Одобрено / Отказ).

Кнопка «+ Новая заявка» → /client/products или сразу /client/applications/new.

Карточки-плитки со счётчиками: «Активные», «Требуют действия».

Empty state: «У вас ещё нет заявок. Подобрать финансирование».

Loading: skeleton-карточки.

Ошибка загрузки: retry-кнопка.

Экран: Каталог продуктов (/client/products)
Карточки продуктов: название, сумма от/до, срок, ставка, короткое описание, теги.

Фильтры: сумма (слайдер), срок, тип продукта.

Подсказка «Подходит для вас» на основе профиля компании (если бэк отдаёт is_recommended).

Кнопка «Оформить» → /client/applications/new?productId=....

Сравнение двух продуктов (опционально) — side-by-side drawer.

Экран: Мастер заявки (/client/applications/new)
Шаги:

Продукт (если не выбран в URL) — выбор карточки.

Потребность — сумма, срок, цель. Показ калькулятора безопасного лимита до ввода суммы (см. 1.4).

Данные компании — подтягиваются из /me/company, редактируемые поля.

Данные заявителя — ФИО, роль, контакты, автозаполнение из профиля.

Документы — drag&drop, OCR-кнопка на каждом файле, отображение распознанных полей.

Проверка и отправка — сводка, чекбокс согласия, кнопка «Отправить».

Функции мастера:

Прогресс-бар с номерами шагов и текущим шагом.

Валидация на шаг: нельзя перейти дальше без корректных полей.

Серверные ошибки маппятся на конкретные поля ({ field: "requested_amount", message: "..." }).

Автосохранение черновика (debounce 1.5с) через PATCH /applications/{id} при status=DRAFT. Показ индикатора «Сохранено 12:34:56».

Восстановление черновика при заходе, если есть DRAFT в бэкенде — баннер «Продолжить черновик?».

Защита от двойной отправки: isSubmitting + idempotency-key в заголовке POST /applications/{id}/submit.

Кнопки «Назад / Далее / Сохранить и выйти».

Сохранение состояния шага в URL (query param step=1) — чтобы F5 не сбрасывал.

На шаге документов — загрузка с прогресс-баром и валидация: тип (pdf, jpg, png), размер (≤10 МБ).

OCR-сценарий: загрузили файл → нажали «Распознать» → бэкенд вернул поля → они подсвечены зелёным, пользователь может отредактировать.

Экран: Калькулятор безопасного лимита (внутри шага 2 мастера)
Отдельный компонент, который можно вызвать и из каталога.

Поля: среднемесячная выручка, среднемесячные расходы, существующая долговая нагрузка (обязательный платёж/мес), срок деятельности (лет), отрасль.

Кнопка «Рассчитать».

Результат:

Диапазон безопасного лимита: min–max с пояснением.

ПДН после оформления: % и цветовой индикатор (<30% зелёный, 30–50% жёлтый, >50% красный).

Рекомендация: «Запрошенная сумма 1 000 000 ₽ превышает безопасный диапазон. Рекомендуем 400 000–600 000 ₽».

Кнопка «Применить рекомендуемую сумму» → подставляет в поле заявки.

Туториал-подсказка «Что такое ПДН» (тултип).

Дисклеймер: «Расчёт ориентировочный, финальное решение — за банком».

Экран: Карточка заявки клиента (/client/applications/:id)
Шапка: номер, продукт, сумма, статус-бейдж, кнопки действий (Отменить, Подписать, Дополнить).

Таймлайн статусов (из ApplicationStatusHistory): дата, статус, комментарий, кто изменил (для клиента — «Банк» / «Вы»).

Текущий этап: человеческое описание («Проверяем данные в ФНС», «Заявка на ручном рассмотрении», «Ожидает вашего действия»).

Блок результата в зависимости от статуса:

APPROVED: сумма, срок, ставка, кнопка «Подписать документы».

APPROVED_WITH_CHANGES: что изменено, почему, кнопки «Принять» / «Отклонить изменения» / «Скорректировать».

NEEDS_INFO: список запрошенных полей/документов, форма дозаполнения, кнопка «Отправить».

REJECTED: причина (без внутренних деталей скоринга), кнопка «Попробовать другой продукт».

DISBURSED: подтверждение выдачи, реквизиты (мок).

Блок документов: список, статус каждого, кнопка «Подписать» (мок), скачивание.

Live-обновления статуса через WebSocket + fallback polling (30 сек).

Экран: «Требуется информация» (внутри карточки)
Список запрошенных полей с описанием от банка.

Форма дозаполнения (те же компоненты, что в мастере).

История запросов информации.

Кнопка «Отправить дополнение» → POST /applications/{id}/supplement.

После отправки — возврат в статус DATA_ENRICHMENT.

Экран: Уведомления (/notifications + dropdown)
Колокольчик в шапке со счётчиком непрочитанных.

Dropdown: последние 5, «Все уведомления».

Страница: список, отметка «прочитано», «прочитать все».

Live-приход по WebSocket ws/notifications/.

Типы: STATUS_CHANGED, NEEDS_INFO, DECISION_READY, DOCUMENT_SIGNED.

Экран: Очередь заявок банка (/bank/applications)
Таблица с колонками: №, клиент/компания, продукт, сумма, статус, дата, менеджер.

Фильтры: статус, продукт, дата, «только мои», сумма (диапазон).

Поиск по номеру/клиенту/компании.

Сортировка.

Пагинация.

Вкладки: «Все», «Требуют ручного решения» (со счётчиком).

Кнопка «Взять в работу» прямо из строки.

Экран: Карточка заявки банка (/bank/applications/:id)
Все данные клиента и компании.

Результаты проверок (моки ЕГРЮЛ, ФНС, БКИ): статус, ключевые поля, флаг «не пройдена».

Скоринг: балл, уровень риска, топ-5 факторов с весами (без «магии», чтобы менеджер мог объяснить клиенту).

Калькулятор безопасного лимита: запрошенная сумма vs безопасный диапазон (для контекста менеджера).

Таймлайн и комментарии (внутренние/клиентские).

Документы — просмотр, скачивание.

Панель действий:

«Одобрить» → модалка с подтверждением.

«Одобрить с изменениями» → модалка с полями: новая сумма, срок, ставка, причина.

«Запросить информацию» → модалка с чек-листом полей/документов и комментарием.

«Отклонить» → модалка с выбором причины из справочника + комментарий.

«Добавить комментарий».

«Назначить на себя».

Кнопки недоступны, если статус не позволяет (disabling + tooltip «Почему недоступно»).

Confirmation-модалки на необратимые действия.

После решения — тост об успехе, инвалидация кеша, обновление таймлайна.

1.4. Мок-слой (MSW)
Зачем: фронт должен запускаться и проходить сквозной сценарий без бэкенда.

Как устроить:

src/api/mocks/browser.ts — настройка MSW, подключение в main.tsx по флагу VITE_USE_MOCKS=true.

src/api/mocks/handlers/ — по модулю на каждый API.

src/api/mocks/fixtures/ — синтетика: 3 компании, 3 пользователя, 5 продуктов, 6 заявок в разных статусах, история, документы.

Имитация задержки и ошибок: await delay(300–800), случайные 500 для проверки error-состояний (управляется флагом).

Имитация state machine: мутации меняют статус в in-memory сторе фикстур, GET возвращает актуальное.

Имитация WebSocket: BroadcastChannel или простой EventEmitter → компонент useMockWebSocket шлёт события при изменении статуса.

Имитация OCR: POST /documents/{id}/ocr возвращает фиктивные поля из маппинга по имени файла.

Имитация скоринга и решения: жёстко зашитые сценарии:

заявка на 500к при выручке 1.5млн → APPROVED;

заявка на 3млн при выручке 1.2млн → APPROVED_WITH_CHANGES (1.5млн);

ИП без истории → NEEDS_INFO;

компания <1 года → REJECTED.

Переключение mock/real: env-переменная VITE_USE_MOCKS=true|false. В README указать оба сценария запуска.

1.5. WebSocket на фронте
Хук useApplicationStatusStream(applicationId) — подключение к ws/applications/{id}/status/.

Хук useNotificationsStream() — подключение к ws/notifications/.

Реконнект с backoff (1с → 2с → 4с → max 30с).

Fallback-поллинг раз в 30 сек, если WS не подключился за 5 сек.

Закрытие соединения при unmount.

Обновление кеша TanStack Query по событию (queryClient.invalidateQueries).

Индикатор соединения в шапке (зелёная точка / «обновление по таймеру»).

1.6. Общие требования
Обработка ошибок: error boundary + тосты. Маппинг кодов: 400 → валидация по полям, 401 → refresh/logout, 403 → 403-страница, 404 → 404, 5xx → «Попробуйте позже».

Loading / empty / error — на каждом экране и списке.

Форматтеры: суммы в ₽ (Intl.NumberFormat), даты dd.MM.yyyy HH:mm, телефоны.

Доступность: label на полях, aria на модалках, keyboard navigation в мастере.

Адаптивность: десктоп-first, планшет ок.

Локализация: строки в src/shared/i18n/ru.ts (без библиотеки, просто объект).

Dev-панель (опционально): переключатель ролей и мок-статусов для демо.
